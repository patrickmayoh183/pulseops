# PulseOps 简历与面试素材

状态：项目实现与上线验收进行中。下列简历文字是验收后可按事实选用的草稿；未落地或未测试的能力不得作为已完成成果。

## 1. 项目的一句话介绍

PulseOps 是基于 Java 与 Vue 的服务巡检平台，提供公开状态页、周期 HTTPS 检查、故障时间线和管理后台，使用一台 ECS 与 MySQL RDS 部署。

计划访问入口为 `pulse.ldjava.com`。在公网验收通过前，应使用“计划部署”而不是“已上线”。仓库 URL 在创建并推送后补充。

## 2. 简历描述草稿

以下段落只有在对应能力实现且验证后才可使用：

> 独立设计并实现 PulseOps 服务巡检平台，使用 Java 21、Spring Boot、Vue 3 与 MySQL，完成从产品范围、接口设计、开发测试到 ECS/RDS 部署的交付。提供公开状态页、管理员监控配置、检查历史、故障进展与操作审计。

可根据实际代码与证据选择两到三个技术要点：

- 使用数据库任务领取与有限时长 lease 管理周期检查，配合有界执行器与网络超时，避免单个慢目标阻塞全部检查；说明实际完成的重启恢复测试。
- 设计连续两次失败触发、连续两次成功恢复的故障状态机，保存检查样本与故障时间线，降低瞬时异常引起的告警抖动。
- 对探测目标实施精确主机白名单、地址限制与禁止重定向，并结合会话认证、CSRF 与操作审计约束管理操作。
- 使用数据库迁移、按监控与时间查询的索引和结果保留策略管理运行数据；用实际查询或测试证据说明效果。

不要加入“支撑百万请求”“高可用分布式”“99.99% SLA”“零重复执行”等没有证据的表述。能解释取舍、展示运行记录，比无法复现的数字更有说服力。

1. **打开公开页**：介绍平台解决的问题，展示真实的最后检查时间与样本数据。
2. **进入服务详情**：说明检查成功率、耗时和错误记录各代表什么，以及为什么成功率不是 SLA。
3. **登录管理台**：展示监控创建、间隔/超时配置、暂停恢复及审计。
4. **讲解故障时间线**：使用明确标注的受控测试证据解释两次失败与两次恢复，不临时破坏生产服务。
5. **展示关键代码与架构**：定位任务领取、状态机、URL 约束和迁移脚本。
6. **说明上线证据与限制**：介绍部署方式、重启恢复、单节点边界和后续改进优先级。

## 4. 常见问题与回答思路

### 为什么做这个项目？

它可以直接维护自己已经部署的服务，并持续产生可验证数据。相比只录入和查询业务表单，巡检还需要处理时间、网络失败、并发、状态变化和安全边界；这些问题能在一个规模可控的项目中形成完整闭环。

### 为什么没有使用微服务、Kafka 或 Redis？

单 ECS、少量监控目标的负载不需要额外中间件。MySQL 已经是已有资源，可以保存配置、结果和任务领取状态。模块划分仍然可以清晰；只有出现独立扩缩容、跨服务事件或吞吐瓶颈的证据后才增加部署复杂度。

### lease 能保证 exactly-once 吗？

不能单凭 lease 做这个保证。lease 解决的是一定时间内谁可以处理任务以及进程退出后的重新领取。检查过慢、lease 过期后重新领取、迟到结果提交等场景仍需要幂等键或执行代次校验。本项目应展示自己实际实现和测试到的保证，并说明单节点边界。

### 为什么两次失败才认为故障？

单次网络抖动可能导致误报。两次连续失败降低故障事件误报，两次连续成功降低事件反复打开、恢复的概率。代价是故障事件创建与恢复确认存在延迟；延迟还受到检查间隔和请求超时影响。服务卡片仍实时展示最近一次样本状态，所以一次成功后的 UP 可能与尚未恢复的 OPEN 事件并存。阈值是项目需求取舍，不是普遍最佳值。

### 暂停检查等于故障恢复吗？

不等于。暂停只表示系统暂时不采样，不证明服务恢复。界面应该区分 PAUSED、PENDING 与 UP，并保留最后检查时间。故障关闭和重启计数的具体行为要与当前实现一致。

### 为什么检查成功率不是 SLA？

这里统计的是一段时间内已经完成的样本。如果进程停机没有采样，缺失的时间不能通过已有成功样本推断为可用。严格的时间可用性还需要处理采样空白、观测误差、维护窗口和独立探测点。

### 做过 SSRF 防护是不是就安全了？

应具体解释实施了哪些约束：管理员权限、允许的协议、精确域名白名单、解析地址分类、重定向策略和端口规则。尤其需要说明 DNS 校验与实际连接是否使用同一个已验证地址；如果客户端再次解析，就不能声称彻底防止 DNS 重绑定。安全能力应由测试和实现细节证明。

### 单节点项目如何监控自己的宕机？

同机探测在整机不可用时会停止，无法独立确认自身故障。这是当前部署的明确限制。下一步可以把探测节点迁移到独立机器或增加外部探测点，同时保留已有 API、状态机与数据模型。

### 数据量增长后如何处理？

先给出实际采样规模。例如五个目标按一分钟检查，每天约 7,200 条结果，这是按配置计算的数量估计，不是压测结论。首先使用合适的查询索引与保留期；只有查询延迟、存储量或归档需求出现后，再考虑日聚合、分区或独立分析存储。

### 为什么有连接池上限为 1 的测试？

故障查询曾在 `RowMapper` 尚未释放外层连接时读取子记录，这会额外申请连接，低容量连接池下可能耗尽。当前实现先把故障列表物化，再查询更新记录，并用上限 1 的测试回归。它说明我们验证了资源使用边界，不代表生产只需一个连接或已经完成性能测试。

### 如何证明项目能稳定运行？

提供真实部署与验收记录：公网访问、检查结果持续写入、状态变化、重启恢复、日志和数据持久化。短时验收不能证明长期稳定性；持续运行天数、错误率和恢复表现需要在真实运行后积累。
